二、update_time_scale 函数详细解析

函数原型：

cstatic float update_time_scale(const JointMoveJPlanner_t jp,
                               const float q_fb[3],
                               const float v_fb[3],
                               float scale_prev)

功能

  • 动态调节 MoveJ 规划器的时间缩放因子 scale，即根据当前关节位置/速度与规划参考值的偏差来放慢或加快轨迹，使轨迹跟随更平滑。
  • 输出的 scale 用于控制 dt_eff = dt_real scale，最终影响关节运动速度。

| 参数 | 含义 |
|------------|------|
| jp | MoveJ 规划器对象，包含当前关节参考位置 q_ref 和速度 v_ref |
| q_fb[3] | 当前前三个关节的反馈角度 |
| v_fb[3] | 当前前三个关节的反馈速度 |

内部变量解释

核心计算步骤

三、如何提高规划器速度（电机运行太慢）

目前你的规划器速度慢，原因主要是：

  • update_time_scale 会根据误差减速，如果位置/速度跟踪误差大，scale 会被限制在较低值（比如 0.15）。
  • MoveJ 本身的速度/加速度受限于 vmax / amax。
  • alpha（一阶滤波）可能使 scale 更新较慢。
  • 任务周期 vTaskDelay(1) 对应约 1ms，可能影响控制响应速度。

优化建议

  • 调整参数
- 增大允许误差： 
cq_tol = {0.05, 0.05, 0.05};
     v_tol = {0.5, 0.5, 0.5};
允许较大误差可以减少减速触发。 - 减小 k 或增大 lambda： - k 太大 → 误差稍大就减速 - lambda 太小 → 速度误差影响小 - 增大 alpha： - 当前 0.10f → 可改为 0.3~0.5，加快 scale 响应
  • 提高关节最大速度/加速度
cg_vmax = {3.0, 3.0, 3.0, ...};
   g_amax = {5.0, 5.0, 5.0, ...};
- 在 JointMoveJ_Start() 中，vs_max 和 as_max 由这些约束决定
  • 优化控制周期
- 减少 vTaskDelay() 延迟或使用更高频率任务 - 确保 dt_real 能精确反映真实周期
  • 检查电机跟随能力
- 如果电机本身无法跟上轨迹，即使调节 scale 也无法提速，需要提升硬件带宽或 PID 增益。

1. 规划器和执行器是怎么串起来的

规划器端在做什么

JointMoveJ_Start() 并不是给每个关节单独规划一条轨迹，而是先计算每个关节位移 dq[i] = q1[i] - q0[i]，然后根据各关节的 vmax / amax 换算出统一标量进度 s(t) 的全局最大速度 vs_max 和最大加速度 as_max。之后，所有关节都靠：

  • q_ref[i] = q0[i] + dq[i] s
  • v_ref[i] = dq[i] sdot
来同步更新。也就是说，真正被规划的是“总进度”，不是 3 个关节各自独立的时间轴。fileciteturn3file1

在 algorithm_task 里，规划线程每个周期会：

  • 从 dm_arm_feedback_pub 里取前三轴反馈；
  • 有新目标时，从当前反馈位置启动 MoveJ；
  • 若 JP_RUNNING，先调用 update_time_scale()；
  • 用 dt_eff = dt_real g_scale 更新规划器；
  • 把 q_ref / v_ref 连同 q_fb / v_fb 一起发布到 movej_ref_pub。fileciteturn3file0
这意味着：规划器每次更新走多远，不只取决于固定周期 dt_real，还取决于动态缩放因子 g_scale。 fileciteturn3file0

执行器端在做什么

执行器线程 DMmotorTask_Entry() 每周期先做两件事：

  • dm_feedback_cache_update()：把电机实际位置/速度做中值滤波和死区处理后，发布为 dm_arm_feedback_pub；
  • 订阅 movej_ref_pub，如果收到新的轨迹参考，就调用 DMmotor_apply_movej_ref()。fileciteturn3file2
DMmotor_apply_movej_ref() 对前三轴的控制逻辑是：
  • 位置命令：pos_cmd[i] = ref->q_ref_rad[i]
  • 速度命令：
vel_cmd[i] = |v_ref| + Kp_track |pos_err| + Kv_track |vel_err|
  • 然后再做：
- 最小跟随速度 v_min_follow = 0.2 - 最大执行速度 v_max_exec = 3.0 - 最后发 pos_ctrl(..., pos_cmd, vel_cmd) 给驱动器。fileciteturn3file2

所以执行器不是纯位置模式，也不是标准 PID。它更像一个：

“位置目标 + 速度前馈 + 误差追赶增益”

的跟踪器。q_ref 决定你要去哪里，v_ref 决定你大致该跑多快，位置/速度误差再额外加一点追赶速度。fileciteturn3file2

2. 时间放缩因子 g_scale 到底影响了什么

关键在这句：

cdt_eff = dt_real  g_scale;
JointMoveJ_Update(&g_movej, dt_eff);

它的物理意义不是“直接给电机降速”，而是：

让规划器内部的时间流逝变慢。 fileciteturn3file0

因为 JointMoveJ_Update() 最终是调用内部标量轨迹更新 s, sdot，再算出新的 q_ref / v_ref。如果你传进去的 dt 变小了，那么本周期 s 前进得就更少，sdot 也会对应更小，于是：

  • q_ref 前进更慢
  • v_ref 更小
  • 整条轨迹执行时间变长 fileciteturn3file1turn3file0
所以：
  • g_scale = 1.0：按原始规划速度跑
  • g_scale = 0.5：规划器相当于半速推进
  • g_scale = 0.15：规划器几乎被压成“很慢的爬行”状态 fileciteturn3file0
这也是你现在感觉“电机运行太慢”的直接原因之一： 不是只有执行器慢，而是规划器自己也在因为误差而主动缩时间轴。 fileciteturn3file0turn3file2

3. update_time_scale() 的真正作用

它本质上是一个跟踪误差驱动的自适应时间缩放器。目标不是让轨迹更快，而是避免“规划器跑得太快，执行器根本追不上”。fileciteturn3file0

我按完整注释方式给你重写一遍：

cstatic float update_time_scale(const JointMoveJPlanner_t jp,
                               const float q_fb[3],
                               const float v_fb[3],
                               float scale_prev)
{
    // 位置误差容忍度。误差等于 0.03 rad 时，归一化后 eq=1
    const float q_tol[3] = {0.03f, 0.03f, 0.03f};   // rad

    // 速度误差容忍度。误差等于 0.20 rad/s 时，归一化后 ev=1
    const float v_tol[3] = {0.20f, 0.20f, 0.20f};   // rad/s


    // 速度误差在综合误差中的权重
    const float lambda = 0.3f;


    // 误差对时间缩放的收缩强度，越大越容易因为误差而减速
    const float k = 1.5f;


    // 最小时间缩放，防止缩到 0，规划器至少保留 15% 速度
    const float scale_min = 0.15f;


    // 一阶低通滤波系数，避免 scale 突然跳变
    const float alpha = 0.10f;


    float eq_n = 0.0f;   // 三个关节中的最大归一化位置误差
    float ev_n = 0.0f;   // 三个关节中的最大归一化速度误差
    float z, scale_raw, scale;


    for (int i = 0; i < 3; i++)
    {
        // 当前关节位置误差，按容忍度归一化
        float eq = fabsf(jp->q_ref[i] - q_fb[i]) / q_tol[i];


        // 当前关节速度误差，按容忍度归一化
        float ev = fabsf(jp->v_ref[i] - v_fb[i]) / v_tol[i];


        // 用“最大值”而不是平均值：任何一个关节误差大，都会拖慢整体
        if (eq > eq_n) eq_n = eq;
        if (ev > ev_n) ev_n = ev;
    }


    // 综合误差：位置误差 + 速度误差加权
    z = eq_n + lambda  ev_n;


    // 原始缩放值：
    // z=0 时，scale_raw=1
    // z 越大，scale_raw 越接近 scale_min
    scale_raw = scale_min + (1.0f - scale_min) / (1.0f + k  z);


    // 对 scale 做一阶滤波，避免一周期快、一周期慢导致抖动
    scale = scale_prev + alpha  (scale_raw - scale_prev);


    // 限幅，保证 scale 始终在 [scale_min, 1.0]
    if (scale < scale_min) scale = scale_min;
    if (scale > 1.0f)      scale = 1.0f;


    return scale;
}

这个函数的控制含义

它做了三件事：

第一，看误差有多大。
拿当前参考值 q_ref / v_ref 和执行器反馈 q_fb / v_fb 比，计算归一化误差。fileciteturn3file0

第二，找最差的那个关节。
不是平均误差，而是取三轴里的最大值。也就是说，只要某一轴明显跟不上，整个轨迹都会被降速。这个策略很保守，但很稳。fileciteturn3file0

第三，把误差映射成时间缩放。
误差越大，scale_raw 越靠近 scale_min，规划器就越慢；误差越小，scale_raw 越接近 1，规划器逐渐恢复全速。最后再经过一阶滤波，避免速度突变。fileciteturn3file0

4. 为什么它会让你“感觉电机特别慢”

结合执行器代码看，慢通常来自下面几层叠加。

第一层：规划器主动减速

这是最直接的。
只要某一轴位置误差超过大约 0.03 rad，或速度误差超过大约 0.20 rad/s，综合误差 z 就会上升，g_scale 会开始往下掉。最小甚至能掉到 0.15。fileciteturn3file0

这意味着规划器内部每次只走原本 15% 的时间步长，整条轨迹会明显拉长。fileciteturn3file0turn3file1

第二层：执行器反馈本身带滤波和死区

执行器发布给规划器的反馈，不是原始编码器值，而是：

  • 位置：5 点中值滤波
  • 位置死区
  • 速度死区 fileciteturn3file2
这会带来两个影响：
  • 反馈有相位滞后：尤其是中值滤波，会让规划器看到的 q_fb 比真实位置慢半拍。
  • 小速度/小位移会被吃掉：死区把微小变化直接置零，低速跟踪时可能让规划器误以为执行器没动。 fileciteturn3file2
这两件事都会增大 update_time_scale() 看到的误差，从而进一步压低 g_scale。fileciteturn3file0turn3file2

第三层：执行器虽然在追赶，但本质上还是“跟参考跑”

DMmotor_apply_movej_ref() 的速度命令是：

|v_ref| + Kp|位置误差| + Kv|速度误差|

也就是说，执行器想跑快，首先得有足够大的 v_ref。但 v_ref 恰恰又是规划器算出来的；一旦规划器被 g_scale 压慢，v_ref 本身就会变小。fileciteturn3file2turn3file1turn3file0

因此这套系统的行为是：

  • 执行器跟不上 → 误差变大
  • 误差变大 → 规划器把 v_ref 变小
  • v_ref 变小 → 执行器收到的基准速度更小
  • 最终整体看起来越来越“保守” fileciteturn3file0turn3file2
---

5. 这套结构的优点和代价

优点是很明显的：

  • 不容易冲过头
  • 电机跟不上时系统会自保
  • 多关节同步更稳
  • 不需要把执行器带宽调到很激进也能工作 fileciteturn3file1turn3file0
代价也很明显：
  • 任何一轴慢，全部轴一起慢
  • 反馈滤波和死区会把“慢”的感觉放大
  • 参数偏保守时，系统会过度降速
  • 轨迹时间不再是固定的，实际执行时间会被动态拉长 fileciteturn3file0turn3file2

6. 你现在这套代码里，我认为最关键的几个“慢”的根源

根源 1：scale_min = 0.15f 太保守

这意味着最坏情况下你允许规划器降到 15% 速度，这个下限非常低。只要执行器某段时间跟踪偏差大，轨迹就会被拉得很长。fileciteturn3file0

根源 2：误差容忍度偏紧

q_tol = 0.03 rad 大约 1.7°，v_tol = 0.20 rad/s 也不算宽。对一个含滤波、死区、RTOS 调度延迟的执行层来说，这样的阈值容易频繁触发降速。fileciteturn3file0turn3file2

根源 3：最大值策略过于保守

你不是取平均误差，而是取最差关节误差 max()。
这意味着只要一轴有噪声、摩擦大、方向符号不一致，全部关节都会一起慢。fileciteturn3file0

根源 4：执行器反馈有滤波滞后

dm_feedback_cache_update() 里对位置做了 5 窗口中值滤波，再死区归零。这个反馈再发给规划器。对于自适应缩时来说，滤波滞后会被解释成“跟不上”。fileciteturn3file2

根源 5：执行层虽然有跟踪增益，但没有真正启用注释里说的 PID

代码里声明了 execute_track_movej_planner_pid 和 PID 参数，但实际没启用，真正执行的是一个简化的 vel_cmd = |v_ref| + ... 逻辑。也就是说，现在的执行层跟踪能力没有你注释写得那么强。fileciteturn3file2

7. 我建议你怎么改，才会“明显变快”

我按优先级给你。

第一优先级：先改 update_time_scale() 的保守程度

最直接的改法：

cconst float q_tol[3] = {0.05f, 0.05f, 0.05f};
const float v_tol[3] = {0.40f, 0.40f, 0.40f};

const float lambda = 0.2f;
const float k = 0.8f;
const float scale_min = 0.40f;
const float alpha = 0.25f;

这样做的效果：

  • 误差容忍更大，不会轻易降速
  • 即便降速，也不会掉到 0.15 那么低
  • alpha 变大后，恢复速度更快，不会长时间趴在低速区
如果你只是想先“跑快一点看看”，这是最值得先试的一步。依据就是当前时间放缩的全部收缩逻辑都在这组参数里。fileciteturn3file0

第二优先级：把“最大误差”改成“更温和的误差聚合”

你现在是：

ceq_n = max(eq_i)
ev_n = max(ev_i)

可以改成 RMS 或平均值，例如：

cfloat eq_sum = 0.0f, ev_sum = 0.0f;
for (int i = 0; i < 3; i++) {
    float eq = fabsf(jp->q_ref[i] - q_fb[i]) / q_tol[i];
    float ev = fabsf(jp->v_ref[i] - v_fb[i]) / v_tol[i];
    eq_sum += eq  eq;
    ev_sum += ev  ev;
}
eq_n = sqrtf(eq_sum / 3.0f);
ev_n = sqrtf(ev_sum / 3.0f);

这样不会因为一轴瞬时差一点点，就把全部关节一起拖慢。
这是结构性优化，比单纯调参更有效。你现在的 max() 是非常保守的同步策略。fileciteturn3file0

第三优先级：减小反馈链路滞后

因为规划器是拿执行器发布的反馈来做时间缩放判断，而反馈又经过：

  • 中值滤波
  • 死区处理 fileciteturn3file2
你可以试：
  • 把位置中值窗口从 5 改成 3
  • 降低 POS_DEADBAND_RAD
  • 降低 VEL_DEADBAND_RAD_S
  • 或者给 update_time_scale() 用“原始反馈”而不是“重滤波反馈”
这一步非常关键，因为你现在的时间缩放其实是“基于滤波后的误差”在缩，不一定反映真实电机能力。fileciteturn3file2turn3file0

第四优先级：增强执行器跟踪能力

现在执行层核心是：

cvel_cmd = |v_ref| + Kp_track|pos_err| + Kv_track|vel_err|

并且限幅到 v_max_exec = 3.0f。fileciteturn3file2

可以尝试：

  • 适当提高 Kp_track
  • 适当提高 Kv_track
  • 适当提高 v_max_exec
  • 或真正启用你注释里预留的 PID 跟踪器
因为只要执行层更容易跟上，误差就会下降，g_scale 自然回升。换句话说，提速不一定只能改规划器，也可以从执行器减误差来间接提速。 fileciteturn3file2turn3file0

第五优先级：检查时间单位是否一致

这里我建议你务必核实一下：

cfloat dt_real = algorithm_task_dt;   // 如果 dwt_get_delta 返回 ms
dt_eff = dt_real  g_scale;
JointMoveJ_Update(&g_movej, dt_eff);

而代码里又定义了：

c#define DT (0.001f) // 1ms 控制周期

这提示我：algorithm_task_dt 的单位你自己也不完全确定。
如果 TrajTimeSync_Update() 期望的是“秒”，而你传的是“毫秒”，或反过来，整个轨迹时基都会不对。这个问题不是我能从当前三份代码里完全确认的，因为 TrajTimeSync_Update() 没贴出来，但它非常值得你优先核实。fileciteturn3file0turn3file1

8. 一句话总结 update_time_scale() 在系统里的定位

它不是普通的“速度倍率”，而是：

一个基于执行器跟踪误差的规划器时间轴调度器。

它的作用是：

  • 执行器跟得上时，让规划器按正常节拍推进；
  • 执行器跟不上时，主动把规划时间轴压缩，降低 q_ref / v_ref 的推进速度，防止轨迹继续把执行器甩开。fileciteturn3file0turn3file2turn3file1
因此它是规划器和执行器之间最关键的耦合点。

9. 你现在最实用的改法

如果你现在目标很明确，就是“别这么慢，先跑快一点”，我建议你先只改这一版：

cstatic float update_time_scale(const JointMoveJPlanner_t jp,
                               const float q_fb[3],
                               const float v_fb[3],
                               float scale_prev)
{
    const float q_tol[3] = {0.05f, 0.05f, 0.05f};
    const float v_tol[3] = {0.40f, 0.40f, 0.40f};

    const float lambda = 0.2f;
    const float k = 0.8f;
    const float scale_min = 0.40f;
    const float alpha = 0.25f;


    float eq_n = 0.0f;
    float ev_n = 0.0f;
    float z, scale_raw, scale;


    for (int i = 0; i < 3; i++)
    {
        float eq = fabsf(jp->q_ref[i] - q_fb[i]) / q_tol[i];
        float ev = fabsf(jp->v_ref[i] - v_fb[i]) / v_tol[i];


        if (eq > eq_n) eq_n = eq;
        if (ev > ev_n) ev_n = ev;
    }


    z = eq_n + lambda  ev_n;


    scale_raw = scale_min + (1.0f - scale_min) / (1.0f + k  z);


    scale = scale_prev + alpha  (scale_raw - scale_prev);


    if (scale < scale_min) scale = scale_min;
    if (scale > 1.0f)      scale = 1.0f;


    return scale;
}

这版通常会比你现在明显更快，因为：

  • 不容易触发减速

  • 减速后最低也不会太慢

  • 恢复全速更快 fileciteturn3file0
